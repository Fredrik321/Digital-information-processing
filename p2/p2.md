### What was built

For P2 we built a **lossless** codec, tested on the dataset from P1 (811 images, `uint8`, shape `(224, 224, 3)`). The implemented interface is:

`compress` returns one `bytes` object; `decompress` returns the original array exactly. The design is a self-describing container (magic `HFM2`) that carries one of two lossless payloads:

- **codec_id 0**, canonical Huffman coding of the raw byte stream, (our implementation)
- **codec_id 1**, a PNG payload produced by Pillow.

The Huffman path is the codec we built; the PNG path is a second payload format for image-shaped arrays, not a claim about Huffman. All reported results are labelled with the coded that produced it, so no number can be misattributed.

`settings` selects the path: `{"image_codec": "auto"}` (default), `{"image_codec": "huffman"}`, or `{"image_codec": "png"}`. In `auto` mode we build both containers from the same raw bytes when the array is image-shaped, and return the smaller; arrays that are not image-shaped always use Huffman. Everything needed to decode is stored in the container itself and is included in our reported sizes. The decoder takes no external metadata: `settings_or_metadata` is accepted only to match the interface, and decoding uses the compressed bytes alone.

### Design: stage names and justifications 

The lossless pipeline has six stages.

**1. Byte stream.** The input array is flattened to its raw C-order bytes (`np.ascontiguousarray(arr).tobytes()`); the dtype string and shape are kept for reconstruction. *Justification:* one byte-level codec then works for every dtype (`uint8`, `int16` and `float32` all round-trip exactly). The cost is that byte-level coding ignores multi-byte structure. An int16 is treated as two unrelated bytes, which is fine for correctness but does not help compression.

**2. Container and side information.** A fixed header is prepended to the payload: magic `HFM2` (4 bytes), the dtype string length (1 byte) and the dtype string, the dimension count (1 byte) and the shape (little-endian `uint32` per dimension), the original byte count (`uint64`), 256 Huffman code lengths (one byte per symbol), a CRC32 of the raw bytes (4 bytes), and the codec id (1 byte). For the 224 x 224 x 3 `uint8` images this header is 292 bytes; for a 1-D `uint8` array it is 284 bytes. *Justification:* the task counts "anything needed to decode" towards the size, so the side information is stored once, explicitly, and is always included in the reported sizes.

**3. Huffman stage (codec_id 0).** Five sub-stages:
- the frequencies of the 256 byte symbols are counted;
- a Huffman tree is built with a heap whose tie-breaking is deterministic (frequency, then insertion order); a single distinct symbol gets a 1-bit code;
- code words are assigned canonically: symbols are sorted by (length, symbol) and codes are assigned incrementally. *Justification:* only the 256 code lengths have to be stored in the header, the decoder rebuilds exactly the same code words, and the construction is reproducible;
- symbols are packed MSB-first, and the final partial byte is zero-padded. The decoder reads exactly the stored symbol count, so padding never becomes data;
- decoding looks codes up by length in the canonical table, and raises if the bits run out early.

*Justification for the whole stage:* Huffman is the optimal prefix code for a zero-order (memoryless) byte model, and it is simple enough that we can explain every part of it.

**4. PNG stage (codec_id 1).** If the array is `uint8` and 2-D, or 3-D with 3 or 4 channels, Pillow can instead encode it as PNG (`optimize=True, compress_level=9`), and those PNG bytes become the payload. PNG internally applies 2-D prediction filters and then DEFLATE (LZ77 matching plus Huffman coding). *Justification:* neighbouring pixels in an image are strongly correlated; a zero-order byte model cannot see that, but prediction filters can. On the development image this path needs 81,978 bytes against 144,568 for pure Huffman.

**5. Integrity check.** The CRC32 of the raw bytes is stored in the header and verified after decoding; the decoder also checks the decoded byte count and, for PNG, the dtype and shape, and raises on any mismatch. *Justification:* a lossless claim should include detection of corrupted input, not only a round trip on clean data. Flipping one bit in a valid container is caught in the tests.

**6. Reconstruction.** The array is rebuilt with `np.frombuffer(raw, dtype).reshape(shape)`, with the dtype and shape taken from the container. *Justification*: the decoder needs nothing beyond the header. dtype and shape are stored explicitly, raw is the exact byte count the header records, and the CRC check in stage 5 runs before this step, so a mismatch is caught before reshaping.

### Byte accounting 

Every size below is a complete output: our totals include the container header, and the baseline's total includes its own framing. The rate is reported as `8 * compressed / original` bits per input byte, so the side information is inside the reported rate, not next to it.

Header layout for the 224 x 224 x 3 `uint8` images:

| field | bytes |
|---|---|
| magic `HFM2` | 4 |
| dtype string length | 1 |
| dtype string `uint8` | 5 |
| dimension count | 1 |
| shape (`uint32` each) | 12 |
| original byte count (`uint64`) | 8 |
| Huffman code lengths (256 symbols) | 256 |
| CRC32 | 4 |
| codec id | 1 |
| **total header** | **292** |

For PNG containers the 256 code-length bytes are all zero and carry no information; they are reserved for the Huffman path. Every PNG container therefore pays 256 bytes that only the Huffman path uses. We kept the header fixed for simplicity and count those bytes in the totals below.

Main results (development image `AMERICAN GOLDFINCH/001.jpg`, 150,528 raw bytes):

| result | total | header + payload | ratio | bits/byte |
|---|---|---|---|---|
| 001.jpg [png] (auto mode) | 81,978 | 292 + 81,686 | 1.836 | 4.357 |
| 001.jpg [huffman] | 144,568 | 292 + 144,276 | 1.041 | 7.683 |
| 132.jpg, unseen [png] | 84,396 | 292 + 84,104 | 1.784 | 4.485 |
| 132.jpg, unseen [huffman] | 144,853 | 292 + 144,561 | 1.039 | 7.698 |

The zero-order byte entropy of the development image is 7.648 bits/byte, so an ideal zero-order coder would need about 143,906 bytes. Our Huffman payload is 144,276 bytes (7.668 bits/byte), within 0.3 % above that bound: the coder is close to optimal for the model it uses. The remaining gap to better codecs comes from modelling, not from the coding itself (see the baseline).

### Tests (shape, data type, empty, tiny, unseen)

The cases cover the brief's checklist: an empty 1-D uint8 array (header-only path, no payload); a single uint8 element and a 3-byte uint8 input; a 1x1 float32; a 1xN int16; a 16x16 uint8 ramp; an 8x8x3 uint8 array of uniformly random bytes; a 32x32 float32 Gaussian noise array; 100 copies of one byte value (the single-symbol Huffman case); and a synthetic 256x256x3 RGB image.

- **Corruption:** one bit is flipped in the middle of a valid container. For a PNG container, Pillow raises on the damaged PNG stream. For a Huffman container, the payload has no internal checksum, so the header CRC is what catches the flip; decompress raises ValueError. Both cases are tested.
- **Unseen file:** `FLAMINGO/132.jpg`, the last file in the sorted dataset, was not used during development. It round-trips exactly through both paths: auto mode (PNG, 84,396 bytes) and forced Huffman (144,853 bytes). The Huffman code is built per file from that file's own byte statistics, so there is no training step that could fail on new data; we still test an unseen file explicitly, as the task requires.

### Baseline comparison (comparable settings)

The baseline is zlib at its default level 6 (`zlib.compress`; DEFLATE, which is LZ77 string matching plus Huffman coding), applied to exactly the same raw byte stream as our forced Huffman path. Both sides are complete outputs: ours includes the 292-byte container header, zlib's includes its own 6 bytes of framing (2-byte header + Adler-32 trailer). Ratio is `original / compressed`; bits/byte is `8 · compressed / original`.

| codec on 001.jpg | complete output (bytes) | ratio | bits/byte |
|---|---|---|---|
| ours, Huffman + header | 144,568 | 1.041 | 7.683 |
| ours, PNG + header | 81,978 | 1.836 | 4.357 |
| baseline, zlib-6 | 105,908 | 1.421 | 5.629 |

Our byte-level Huffman is larger than zlib-6 here, because LZ77 removes repeated substrings that a zero-order byte model cannot represent. The Huffman payload sits within 0.26 % of the zero-order entropy bound, so the coder is not the weakness, but rather the model is. The PNG path is smaller than zlib-6 because PNG applies 2-D prediction filters before DEFLATE, which exploits spatial correlation that a byte-level model cannot see. Each codec is measured in forced mode and labelled from the container header, so these are independent measurements, not estimates.
### Where the method should not be used (documented failures)

- **Already-compressed data.** The JPEG file of the development image (22,236 bytes on disk) compresses to 22,455 bytes (ratio 0.990). The Huffman payload is 65 bytes smaller than the file itself, but the 284-byte container header more than cancels that saving. On already-compressed data, Huffman finds almost nothing to remove and makes the header dominate.
- **Tiny inputs.** A 3-byte input becomes 285 bytes (ratio 0.011), and a 1-byte input becomes 285 bytes. The fixed header dominates, so for small data the method should not be used; store the raw bytes instead.
- **Byte-level Huffman on photographs.** Decoded JPEG pixels are close to random at the byte level (entropy 7.648 bits/byte), so forced Huffman only reaches a ratio of 1.04 on this data. This is the setting where a zero-order byte model is the wrong choice, not where the coder fails. `auto` mode selects the PNG path for photographs for this reason.

The only source of randomness is `numpy.random.default_rng(0)` in the test cell, which is fixed.
