### What was built

For P2 we built a **lossless** codec, tested on the dataset from P1 (811 images, `uint8`, shape `(224, 224, 3)`). The implemented interface is:

`compressed = compress(data, settings)`
`reconstructed = decompress(compressed, settings_or_metadata)`

`compress` returns one `bytes` object; `decompress` returns the original array exactly. The design is a self-describing container (magic `HFM2`) that carries one of two lossless payloads:

- **codec_id 0**, canonical Huffman coding of the raw byte stream, our own implementation.
- **codec_id 1**, a PNG payload produced by Pillow.

The Huffman path is the codec we built; the PNG path is a second payload format for image-shaped arrays, not a claim about Huffman. All reported results are labelled with the codec that produced them (read back from the container header), so no number can be misattributed.

`settings` selects the path: `{"image_codec": "auto"}` (default), `{"image_codec": "huffman"}`, or `{"image_codec": "png"}`. A second key, `{"predictor": "none" | "horizontal" | "vertical" | "auto"}`, applies a delta pre-processing step to the Huffman path only; the PNG path ignores it. In `auto` mode we build both containers from the same raw bytes when the array is image-shaped, and return the smaller; arrays that are not image-shaped always use Huffman. Everything needed to decode is stored in the container itself and is included in our reported sizes. The decoder takes no external metadata: `settings_or_metadata` is accepted only to match the interface, and decoding uses the compressed bytes alone.

### Stages

The lossless pipeline has seven stages.

**1. Byte stream.** The input array is flattened to its raw C-order bytes (`np.ascontiguousarray(arr).tobytes()`); the dtype string and shape are kept for reconstruction. *Justification:* one byte-level codec then works for every dtype (`uint8`, `int16` and `float32` all round-trip exactly). The cost is that byte-level coding ignores multi-byte structure. An `int16` is treated as two unrelated bytes, which is fine for correctness but does not help compression.

**2. Container and side information.** A fixed header is prepended to the payload: magic `HFM2` (4 bytes), the dtype string length (1 byte) and the dtype string, the dimension count (1 byte) and the shape (little-endian `uint32` per dimension), the original byte count (`uint64`), 256 Huffman code lengths (one byte per symbol), a CRC32 of the raw bytes (4 bytes), the codec id (1 byte) and the predictor id (1 byte). For the 224 x 224 x 3 `uint8` images this header is 293 bytes; for a 1-D `uint8` array it is 285 bytes. *Justification:* the task counts "anything needed to decode" towards the size, so the side information is stored once, explicitly, and is always included in the reported sizes.

**3. Huffman stage (codec_id 0).** Five sub-stages:
- the frequencies of the 256 byte symbols are counted;
- a Huffman tree is built with a heap whose tie-breaking is deterministic (frequency, then insertion order); a single distinct symbol gets a 1-bit code;
- code words are assigned canonically: symbols are sorted by (length, symbol) and codes are assigned incrementally. *Justification:* only the 256 code lengths have to be stored in the header, the decoder rebuilds exactly the same code words, and the construction is reproducible;
- symbols are packed MSB-first, and the final partial byte is zero-padded. The decoder reads exactly the stored symbol count, so padding never becomes data;
- decoding looks codes up by length in the canonical table, and raises if the bits run out early.

*Justification for the whole stage:* Huffman is the optimal prefix code for a zero-order (memoryless) byte model, and it is simple enough that we can explain every part of it.

**4. Predictor (optional, Huffman path only).** For image-shaped `uint8` arrays, the samples can be delta-transformed before byte counting. Horizontal: each sample minus its left neighbour (first column stored verbatim). Vertical: each sample minus its upper neighbour (first row stored verbatim). All arithmetic wraps mod 256 (`uint8`). The decoder inverts exactly with `np.cumsum(..., dtype=np.uint8)`. *Justification:* neighbouring pixels are highly correlated, so the residual distribution is concentrated near zero while the raw byte distribution is near-uniform. The Huffman coder is unchanged; only the input distribution changes. One header byte records which predictor was used (0 = none, 1 = horizontal, 2 = vertical) so the decoder needs no external hint. On the development image, forced Huffman drops from 144,569 to 94,637 bytes with the horizontal predictor: a 35 % reduction from a few lines of preprocessing.

**5. PNG stage (codec_id 1).** If the array is `uint8` and 2-D, or 3-D with 3 or 4 channels, Pillow can encode it as PNG (`optimize=True, compress_level=9`), and those PNG bytes become the payload. PNG internally applies adaptive 2-D prediction filters and then DEFLATE (LZ77 matching plus Huffman coding). *Justification:* neighbouring pixels in an image are strongly correlated; a zero-order byte model cannot see that, but prediction filters can. On the development image this path needs 81,979 bytes against 144,569 for pure Huffman.

**6. Integrity check.** The CRC32 of the raw bytes is stored in the header and verified after decoding; the decoder also checks the decoded byte count and, for PNG, the dtype and shape, and raises on any mismatch. *Justification:* a lossless claim should include detection of corrupted input, not only a round trip on clean data. Flipping one bit in a valid container is caught in the tests.

**7. Reconstruction.** The array is rebuilt with `np.frombuffer(raw, dtype).reshape(shape)`, with the dtype and shape taken from the container. *Justification:* the decoder needs nothing beyond the header. The dtype and shape are stored explicitly, and raw is the exact byte count the header records. The CRC is checked after decoding and predictor inversion, before the final returned array; a mismatch raises.

### Byte accounting

Every size below is a complete output: our totals include the container header, and the baselines total includes its own framing. The rate is reported as `8 * compressed / original` bits per input byte, so the side information is inside the reported rate, not next to it.

Header layout for the 224 x 224 x 3 `uint8` images:

| field | bytes |
|---|---|
| magic `HFM2` | 4 |
| dtype string length | 1 |
| dtype string `uint8` | 5 |
| dimension count | 1 |
| shape (`uint32` each) | 12 |
| original byte count (`uint64`) | 8 |
| Huffman code lengths (256 symbols) | 256 |
| CRC32 | 4 |
| codec id | 1 |
| predictor id | 1 |
| **total header** | **293** |

For PNG containers the 256 code-length bytes are all zero and carry no information; they are reserved for the Huffman path. Every PNG container therefore pays 256 bytes that only the Huffman path uses. We kept the header fixed for simplicity and count those bytes in the totals below.

Main results (development image `AMERICAN GOLDFINCH/001.jpg`, 150,528 raw bytes):

| result | total | header + payload | ratio | bits/byte |
|---|---|---|---|---|
| 001.jpg [png] (auto mode) | 81,979 | 293 + 81,686 | 1.836 | 4.357 |
| 001.jpg [huffman] | 144,569 | 293 + 144,276 | 1.041 | 7.683 |
| 001.jpg [huffman + horizontal] | 94,637 | 293 + 94,344 | 1.591 | 5.030 |
| 132.jpg, unseen [png] | 84,397 | 293 + 84,104 | 1.784 | 4.485 |
| 132.jpg, unseen [huffman] | 144,854 | 293 + 144,561 | 1.039 | 7.698 |

The zero-order byte entropy of the development image is 7.648 bits/byte, so an ideal zero-order coder would need about 143,905 bytes. Our Huffman payload is 144,276 bytes (7.668 bits/byte), within 0.26 % above that bound: the coder is close to optimal for the model it uses. The horizontal-delta stream has its own zero-order entropy, about 5.03 bits/byte on this image, so the Huffman+horizontal payload sits close to that lower bound too. The coder is optimal for whichever model it is given; the predictor is what changes the model. The remaining gap to stronger codecs comes from modelling, not from the coding itself (see the baseline).

### Tests (shape, data type, empty, tiny, unseen)

Every round trip is asserted exactly: the decoded array must match the original in shape, dtype, and element-wise equality (`np.array_equal`), including the `float32` cases where equality is still the correct check because we compress raw bytes, not values. The cases cover the brief's checklist: an empty 1-D `uint8` array (header-only path, no payload); a single `uint8` element and a 3-byte `uint8` input; a 1x1 `float32`; a 1-D `int16`; a 16x16 `uint8` ramp; an 8x8x3 `uint8` array of uniformly random bytes; a 32x32 `float32` Gaussian noise array; 100 copies of one byte value (the single-symbol Huffman case); and a synthetic 256x256x3 RGB image.

- **Corruption:** one bit is flipped in the middle of a valid container. For a PNG container, Pillow raises on the damaged PNG stream. For a Huffman container the payload has no internal checksum, so the header CRC is what catches the flip; `decompress` raises `ValueError`. Both cases are tested, and the Huffman case is repeated with a predictor active.
- **Predictors:** the delta transforms and their `cumsum` inverses are checked for exact equality on real images. Round-trips are run with `{"predictor": "horizontal"}` and `{"predictor": "vertical"}` on image-shaped arrays. On non-image arrays the predictor is ignored and the header records `"none"`; this is asserted for a 1-D `int16`, a 1-D `uint8`, and a 2-D `float32`. Invalid predictor names and invalid predictor ids in the header both raise `ValueError`.
- **Unseen file:** `FLAMINGO/132.jpg`, the last file in the sorted dataset, was not used during development. It round-trips exactly through both paths: auto mode (PNG, 84,397 bytes) and forced Huffman (144,854 bytes). The Huffman code is built per file from that file's own byte statistics, so there is no training step that could fail on new data; we still test an unseen file explicitly, as the task requires.

### Baseline comparison (comparable settings)

The baseline is zlib at its default level 6 (`zlib.compress`; DEFLATE, which is LZ77 string matching plus Huffman coding), applied to exactly the same raw byte stream as our forced Huffman path. Both sides are complete outputs: ours includes the 293-byte container header, zlib's includes its own 6 bytes of framing (2-byte header + Adler-32 trailer). Ratio is `original / compressed`; bits/byte is `8 · compressed / original`.

| codec on 001.jpg | complete output (bytes) | ratio | bits/byte |
|---|---|---|---|
| ours, Huffman + header | 144,569 | 1.041 | 7.683 |
| ours, Huffman + horizontal delta + header | 94,637 | 1.591 | 5.030 |
| ours, PNG + header | 81,979 | 1.836 | 4.357 |
| baseline, zlib-6 | 105,908 | 1.421 | 5.629 |

On raw pixels our zero-order Huffman is larger than zlib-6, because LZ77 removes repeated substrings that a byte-level model cannot represent. The Huffman payload sits within 0.26 % of the zero-order entropy bound, so the coder is not the weakness; the model is. Adding a single horizontal delta as preprocessing — with the Huffman coder unchanged — lifts the ratio to 1.591 and beats zlib-6 on the same image. The PNG path is still smaller because PNG combines adaptive per-row filters (Sub, Up, Average, Paeth) with DEFLATE; that is a richer model on top of the same class of predictor, not a different coder. Each codec is measured in forced mode and labelled from the container header, so these are independent measurements, not estimates.

The zlib-6 row sees the raw bytes, matching the no-predictor Huffman row. The Huffman+horizontal row sees a transformed input, so that comparison isolates the effect of the predictor rather than being a strict head-to-head codec comparison.
### Where the method should not be used

- **Already-compressed data.** The JPEG file of the development image (22,236 bytes on disk) compresses to 22,455 bytes (ratio 0.990). The Huffman payload is 66 bytes smaller than the file itself, but the 285-byte container header more than cancels that saving. On already-compressed data, Huffman finds almost nothing to remove and makes the header dominate.
- **Tiny inputs.** A 3-byte input becomes 286 bytes (ratio 0.011), and a 1-byte input becomes 286 bytes. The fixed header dominates, so for small data the method should not be used; store the raw bytes instead.
- **Byte-level Huffman on photographs, without a predictor.** Decoded JPEG pixels are close to random at the byte level (entropy 7.648 bits/byte), so forced Huffman on raw bytes only reaches a ratio of 1.04. This is the setting where a zero-order byte model is the wrong choice, not where the coder fails: adding a single horizontal delta lifts the ratio to 1.591 with the same coder, and `auto` mode selects the PNG path for images anyway.
